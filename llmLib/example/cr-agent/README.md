# Go 代码审查工具 (cr-agent)

使用三 Agent 范式实现的 Go 代码审查工具。

## 架构设计

### 三 Agent 范式

1. **Planner（规划者）**: 分析代码，决定要审查哪些维度
   - 使用 `complete` 和 `ParseInto` 产出维度清单
   - 输出结构化 JSON: `{"dimensions":["并发安全","错误处理","性能"]}`

2. **Generator（生成者）**: 对每个维度并行审查
   - 使用 Sectioning 模式，各维度独立审查
   - 每个维度产出结构化发现

3. **Evaluator（评估者）**: 汇总后评估报告是否充分
   - 使用 Evaluator-Optimizer 模式
   - 评分 >= 0.8 结束，否则反馈给 Generator 补充

4. **IntentRouter（意图路由器）**: 前置判断输入是否为代码
   - 代码模式匹配 + LLM 判断
   - 非代码输入路由到普通回答

## 思考：三 Agent 是否必要？

### 什么情况下三 Agent 更有价值？

1. **长而复杂的代码**: 当代码超过 200-300 行，单一调用可能遗漏细节
2. **多角度深度审查**: 需要从多个专业角度（安全、性能、架构）深入分析
3. **可迭代改进**: 需要评估→反馈→改进的迭代循环
4. **Token 预算控制**: 分段调用可以更好地控制成本

### 什么情况下单次调用就够了？

1. **短代码片段**: 50 行以内的简单函数
2. **单一关注点**: 只需要检查特定问题（如并发安全）
3. **快速反馈**: 需要即时结果，不关心深度
4. **简单修复**: 已知问题，只需要确认修复方案

### 总结

对于**生产级代码审查**，三 Agent 模式的优势在于：
- **分工明确**: 每个 Agent 专注于自己的领域
- **质量保障**: Evaluator 确保报告充分
- **可扩展性**: 可以轻松添加新的审查维度

对于**快速检查**或**简单代码**，单次调用更高效。

## 对比实验建议

建议做一个对比实验：
1. 写一版单次调用版代码审查，把所有要求塞进一个提示词
2. 用同一段代码跑两版
3. 对比：质量（问题覆盖率、建议质量）和 Token 消耗

对短代码来说，单次调用可能又快又省，质量也够；
只有面对长而复杂的代码，三 Agent 的分维度和自我把关才更能体现价值。
