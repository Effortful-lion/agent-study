# llmLib 后续目标定位

> 参考项目：[Pi (earendil-works/pi)](https://github.com/earendil-works/pi) — AI Agent 工具包，统一 LLM API + Agent 运行时 + TUI + 自扩展编程 Agent CLI，78.7k+ stars。

---

## 一、定位对标：Go 版 AI Agent 工具包

将 llmLib 从 LLM 开发学习库演进为 **Go 语言生态中的 AI Agent 工具包**，对标 Pi 在 TypeScript/Node.js 生态中的定位。

Pi 的核心四层架构：

```
pi-coding-agent  (CLI)       ← 面向用户的产品
pi-tui           (TUI)       ← 终端交互界面
pi-agent-core    (运行时)     ← Agent 执行引擎 + 工具调用 + 状态管理
pi-ai            (LLM API)   ← 多提供商统一调用层
```

## 二、当前能力盘点

### 2.1 AI 调用层（对标 pi-ai）

| 能力 | 状态 | 说明 |
|------|------|------|
| 多 Provider 接入（8 个服务商） | 已有 | OpenAI、DeepSeek、Doubao、Claude、Zhipu、Tongyi、Kimi、Qwen |
| 统一 Provider 接口 | 已有 | `Provider` + `ToolCallProvider` 两级接口 |
| 流式调用 | 已有 | `ChatStream()` + SSE 解析 |
| 工具调用（Function Calling） | 已有 | OpenAI 原生 + Claude 协议转换 |
| 路由调度 + 故障转移 | 已有 | 3 种策略：默认/最低价格/最低延迟 |
| 延迟统计（P50/P95） | 已有 | 线程安全的 `LatencyMetrics` |
| 错误诊断 | 已有 | 网络/鉴权/限流/5xx 分类 + 排查建议 |
| 环境变量自动装配 | 已有 | `.env` 加载 + `LoadAll()` 一键初始化 |
| Token 估算 | 已有 | 基于字符数的粗略估算 |

### 2.2 Agent 运行时（对标 pi-agent-core）

**已有：**

| 能力 | 说明 |
|------|------|
| Think-Act-Observe 状态机 | 基础循环：thinking → acting → done/error |
| 工具注册与调用 | `Tool` 接口 + `Registry` 注册表 + 参数解析 |
| ReAct 范式兼容 | 模型不用 Function Calling 时，自动解析 ReAct 格式的工具调用 |
| 首次调用防偷懒 | 首轮未调用工具时，自动追加提示要求使用工具 |
| 未调用工具检测 | 检测还有未使用的工具时，提示模型检查是否需要继续 |
| 重复动作检测 | 同参数同工具重复调用超过 3 次自动跳过 |
| 工具失败优雅降级 | 错误作为 tool result 反馈给模型，不直接终止 |
| 指数退避重试 | `RetryWithBackoff` 用于工具调用失败重试 |
| 预算控制 | 步数/Token/时长 上限 + 动作重复上限 |
| 事件系统 | 分层事件：step/model/tool/result/control |
| 文件会话持久化 | `FileStore` 保存/恢复 State JSON |
| 错误分类 | 10 种错误类别 + `ClassifyError` 自动识别 |

**缺失：**

| 能力 | 说明 |
|------|------|
| 上下文窗口管理 | 无消息截断、摘要压缩、滑动窗口，长对话会超出模型限制 |
| 长期记忆 | 无向量存储、无 RAG，每个会话独立，无法跨会话复用知识 |
| 并行工具调用 | `stepAct` 中工具串行执行，不支持同轮并发调用多个工具 |
| 子 Agent 委派 | 不支持 Agent 将子任务委派给另一个 Agent |
| 人机协同（Human-in-the-Loop） | 无审批/确认机制，工具直接执行 |
| 结构化输出 | 无 constrained generation / JSON mode 支持 |
| 流式输出给调用方 | 事件通过 channel 收集但无 SSE 推流给客户端 |
| 工具执行超时 | 单个工具调用没有超时控制 |
| 模型级故障转移 | Agent 只绑定一个 Provider，模型挂了不会自动切换 |
| 上下文压缩 | 长对话无自动摘要或关键信息提取 |
| 可观测性 | 无 tracing、无 metrics 埋点 |
| 检查点恢复 | 会话可保存但不能从中间失败步骤恢复重试 |
| Prompt 缓存优化 | 无 prompt caching 支持 |
| 多 Agent 协作 | 无多 Agent 通信/协调机制 |

### 2.3 模式与编排（pattern/ 目录）

5 种模式均有骨架实现（`Pattern` 接口 + `Execute`），但**模式本身不内置 LLM 调用逻辑**，需要调用方注入 `StepFunc`：

| 模式 | 状态 | 说明 |
|------|------|------|
| Chain（链式） | 有骨架 | 顺序执行步骤，StepFunc 由调用方注入 |
| Router（路由） | 有骨架 | 按条件分发，StepFunc 由调用方注入 |
| Parallel（并行） | 有骨架 | goroutine 并发，StepFunc 由调用方注入 |
| Orchestrator（编排者-工作者） | 有骨架 | Plan → Execute → Synthesize，StepFunc 由调用方注入 |
| Evaluator-Optimizer（评估器-优化器） | 有骨架 | 生成→评估→反馈循环，StepFunc 由调用方注入 |

**缺失：** 没有开箱即用的 LLM 集成版（如 "用 LLM 自动规划子任务" 的 Orchestrator），需要调用方自己把 Prompt + 模型调用包进 StepFunc。

### 2.4 通用基础设施（state/ 目录）

| 能力 | 状态 | 说明 |
|------|------|------|
| 通用状态机 Machine | 已有 | 状态转换 + 条件判断 + 中间件 |
| 工作流引擎 Workflow | 已有 | 链式 Do() API + Step 重试/超时 |
| 中间件体系 | 已有 | Retry / Timeout / Recovery / Log |

### 2.5 工具与 Schema

| 能力 | 状态 | 说明 |
|------|------|------|
| Tool 接口 + Registry | 已有 | 注册、查找、生成 ToolDefs |
| JSON Schema 自动生成 | 已有 | reflect 递归从 Go 结构体生成 JSON Schema |
| SchemaTool 接口 | 已有 | 支持返回 JSON Schema 格式参数的工具 |

### 2.6 上层产品（TUI / CLI）

**全部缺失。** 目前只有库代码，没有可执行的产品形态：
- 无交互式 CLI（对标 pi-coding-agent）
- 无 TUI（对标 pi-tui）
- 无 IDE 集成

## 三、后续演进方向（参考 Pi）

### Phase 1：Agent 运行时完善

优先补齐核心运行时缺失的关键能力：

1. **上下文窗口管理** — 消息截断 / 滑动窗口 / 旧消息摘要，保证长对话不超 Token 限制
2. **流式输出** — Agent 输出支持 SSE 推流给调用方
3. **人机协同** — 工具调用前可选的审批/确认回调
4. **工具执行超时** — 单个工具调用的超时控制
5. **模型级故障转移** — Agent 支持 Router，模型挂了自动切换
6. **并行工具调用** — 同轮多个工具调用改为 goroutine 并发执行

### Phase 2：产品化 — 编程 Agent CLI

1. **交互式 REPL** — 终端多轮对话
2. **项目感知** — 自动读取项目结构、构建上下文
3. **编程工具集** — 文件读写、命令执行、Git 操作
4. **自扩展能力** — Agent 可自主编写新工具（Pi 核心亮点）

### Phase 3：终端 UI + 安全隔离

1. **TUI 界面** — 基于 bubbletea，多面板（对话/工具/diff/状态栏）
2. **容器化沙箱** — Docker/Podman 中执行工具，隔离文件系统和网络

### Phase 4：长期能力

1. **长期记忆与 RAG** — 向量存储 + 知识检索
2. **多 Agent 协作** — Agent 间通信与协调
3. **可观测性** — tracing + metrics
4. **插件系统** — 第三方工具分发机制
5. **IDE 集成** — VS Code / JetBrains 插件
